## Objective and scope

Persist sanitized scoped diff and real test evidence, including partial failures.

Out of scope: Automatic merge, fabricated successful tests or record-schema adoption.

## Implementation sequence

1. Collect against the fixed base with explicit coverage for committed, staged, unstaged and untracked changes; define deduplication, rename and binary behavior.
2. Record base/head SHA, branch, changed files, real commands/codes/durations and evidence level through a trusted producer mapping.
3. Apply byte caps while collecting, then redact before persistence and response. Scan filenames, diagnostics, test text and cost notes as well as diff/log bodies.
4. Report collection errors, missing commands, binary omissions, truncation and unknown cost as limitations. Failed collection cannot be represented as empty success.

## Required acceptance matrix

Map each row ID to named tests or executed experiments and recorded evidence in the
PR. Cover the actual failure boundary, not just a mock returning the expected value.
For docs/research rows, use content, link or experiment verification as appropriate.
Every named variant within a scenario is required, not a choice of one example.

| ID | Scenario | Required observable result |
| --- | --- | --- |
| B13-01 | Added/deleted/renamed/untracked and staged/committed mix | Expected complete scoped file set and diff; parent/unrelated files absent. |
| B13-02 | Tests fail or omit command evidence | Real nonzero code or explicit limitation; result cannot claim verified success. |

## Validation and evidence to publish

1. Run focused scenarios above, then `node --test` and
   `node examples/fallback-demo.mjs` from the repo root on Node 24.22.1.
   Capture actual process exits; a formatter/pipeline exit is not a test exit.
   Docs-only work uses relevant content/link checks and required baseline checks;
   do not add unit tests that merely repeat prose.
2. Record OS/architecture, Node and Git/host versions when applicable, base SHA,
   command, exit code, test names and pass/fail/not_run for every row.
   A missing required host/platform experiment is a blocker for that acceptance claim.
3. State the strongest observed evidence (local tests, real subprocess, pinned host,
   or use on project). List missing gates and remaining limitations explicitly.
   Use temporary state/repos, fixture providers and sanitized transcripts.
4. Review once during implementation for design/authority/failure paths; fix findings.
   After completion, review the entire final diff and every matrix row again, correct
   findings and rerun affected checks. A green suite alone does not complete either review.
5. Commit, push, open/update the one task PR and verify its URL, base/head and remote
   head SHA. Include matrix, review findings/fixes, final validation and limitations.
   Stop at published PR ready for review; merging requires task-specific authorization.
