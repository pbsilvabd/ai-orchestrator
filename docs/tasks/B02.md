# B02 — Practical documentation templates

## Pickup and delivery

- Status at baseline `d5cdcea`: Merged through PR #11; historical acceptance contract.
- Prerequisites: None for history; any follow-up needs a separately scoped task.
- First read [AGENTS](../../AGENTS.md), the [execution protocol](../task-execution.md),
  the [backlog index](../backlog.md), the normative [task contract](../task-contract.md)
  and the relevant ADRs. Fetch current state; this baseline is not permission to
  overwrite newer work.
- Expected code ownership: docs/templates; CONTRIBUTING.md; documentation references.
- Common documentation: worklog and validation always; contract/ADR when behavior or
  authority changes; handoff/roadmap when the next action or milestone changes.
- Delivery: one task ID, one branch, one PR. Follow the complete implementation,
  validation, two review passes, correction and publication cycle below. Existing
  completed/open deliveries are updated or inspected, never duplicated.

## Objective and scope

Templates describe actual decisions and evidence without fabricated current status.

Out of scope: Runtime changes or rewriting append-only history.

## Implementation sequence

1. Represent proposed, accepted and superseded decisions without assuming acceptance.
2. Represent unmerged implementation and merged history separately.
3. Check every relative link from the destination document; explain proportionate template adaptations.
4. Keep the normative contract above templates and preserve existing historical entries.

## Required acceptance matrix

Map each row ID to named tests or executed experiments and recorded evidence in the
PR. Cover the actual failure boundary, not just a mock returning the expected value.
For docs/research rows, use content, link or experiment verification as appropriate.
Every named variant within a scenario is required, not a choice of one example.

| ID | Scenario | Required observable result |
| --- | --- | --- |
| B02-01 | Example copied to destination | Relative links resolve and placeholders are removed. |
| B02-02 | Proposed or unmerged example | No invented gate pass, merge claim or current next action. |
| B02-03 | Documentation-only delivery | Content/link checks recorded; no tests invented just to mirror prose. |

## Validation and evidence to publish

1. Run focused scenarios above, then `node --test` and
   `node examples/fallback-demo.mjs` from the repo root on Node 24.22.1.
   Capture actual process exits; a formatter/pipeline exit is not a test exit.
   Docs-only work uses relevant content/link checks and required baseline checks;
   do not add unit tests that merely repeat prose.
2. Record OS/architecture, Node and Git/host versions when applicable, base SHA,
   command, exit code, test names and pass/fail/not_run for every row.
   A missing required host/platform experiment is a blocker for that acceptance claim.
3. State the strongest observed evidence (local tests, real subprocess, pinned host,
   or use on project). List missing gates and remaining limitations explicitly.
   Use temporary state/repos, fixture providers and sanitized transcripts.
4. Review once during implementation for design/authority/failure paths; fix findings.
   After completion, review the entire final diff and every matrix row again, correct
   findings and rerun affected checks. A green suite alone does not complete either review.
5. Commit, push, open/update the one task PR and verify its URL, base/head and remote
   head SHA. Include matrix, review findings/fixes, final validation and limitations.
   Stop at published PR ready for review; merging requires task-specific authorization.

## Final completion check

- [ ] Prerequisites and current remote inspected; scope and contracts respected.
- [ ] Every matrix row has observed evidence; required failures/missing gates resolved.
- [ ] Relevant regression scenarios, full suite, demo and diff checks passed.
- [ ] Both review passes completed and all blocking findings fixed/revalidated.
- [ ] Documentation reflects the result without rewriting append-only history.
- [ ] One PR published and remote head verified; final reply gives URL/SHA and results.

Do not stop after a plan, branch creation or first implementation. Continue through
publication within the same active work session. If an actual external blocker prevents
completion, use the [blocked-work procedure](../task-execution.md#blocked-work),
publish safe partial work as a draft when possible, and report it as incomplete.
