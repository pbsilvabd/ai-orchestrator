## Objective and scope

A newly accepted task has a real allowed repository, a fixed base commit and a legal unused branch.

Out of scope: Worker launch, worktree creation, routing, transport or accepting arbitrary revisions.

## Implementation sequence

1. Specify and document validation/error/replay ordering before editing: validate request structure, configured identity and static authorization/budget limits, then resolve client-scoped idempotency by the original canonical payload. Defer new-request filesystem/ref/branch validation until after this lookup; an identical replay must not recheck repository existence, branch availability or a moving ref. Document how configuration changes affect authorization without silently widening it.
2. For a new request canonicalize repository and allowed roots using real filesystem paths, verify directory boundaries after symlink/junction resolution, and inspect a real Git repository using argument arrays without a shell.
3. Accept a single commit-ish resolving to a commit; reject ranges, leading-option values and missing refs. Validate the branch using Git ref rules and require it to be absent locally.
4. Persist the fixed full base SHA as immutable metadata without replacing the user's request or changing payload hashing. Document how older records without this metadata remain readable but cannot execute until explicitly resolved.
5. Update existing service fixtures to initialize actual temporary repositories; ensure rejection happens before task/index or workspace creation. Keep result and replay semantics intact.

## Required acceptance matrix

Map each row ID to named tests or executed experiments and recorded evidence in the
PR. Cover the actual failure boundary, not just a mock returning the expected value.
For docs/research rows, use content, link or experiment verification as appropriate.
Every named variant within a scenario is required, not a choice of one example.

| ID | Scenario | Required observable result |
| --- | --- | --- |
| B03-01 | Valid allowed repo, branch and base | One accepted record contains a full commit SHA; no workspace or subprocess worker starts. |
| B03-02 | Same key/payload after branch creation, ref movement or repo removal | Returns original task ID/base SHA; changed payload still returns idempotency_conflict. |
| B03-03 | Nonexistent repo, missing ref, range a..b or leading-option ref | Documented contract error; task/index bytes and Git refs unchanged. |
| B03-04 | Path-prefix sibling and symlink/junction escape | authorization_denied after canonical containment check; explicitly report any platform case not run. |
| B03-05 | Existing branch, invalid branch, linked worktree and dirty parent | Branch collision rejected; supported repo identity documented; user files unchanged. |

## Validation and evidence to publish

1. Run focused scenarios above, then `node --test` and
   `node examples/fallback-demo.mjs` from the repo root on Node 24.22.1.
   Capture actual process exits; a formatter/pipeline exit is not a test exit.
   Docs-only work uses relevant content/link checks and required baseline checks;
   do not add unit tests that merely repeat prose.
2. Record OS/architecture, Node and Git/host versions when applicable, base SHA,
   command, exit code, test names and pass/fail/not_run for every row.
   A missing required host/platform experiment is a blocker for that acceptance claim.
3. State the strongest observed evidence (local tests, real subprocess, pinned host,
   or use on project). List missing gates and remaining limitations explicitly.
   Use temporary state/repos, fixture providers and sanitized transcripts.
4. Review once during implementation for design/authority/failure paths; fix findings.
   After completion, review the entire final diff and every matrix row again, correct
   findings and rerun affected checks. A green suite alone does not complete either review.
5. Commit, push, open/update the one task PR and verify its URL, base/head and remote
   head SHA. Include matrix, review findings/fixes, final validation and limitations.
   Stop at published PR ready for review; merging requires task-specific authorization.
