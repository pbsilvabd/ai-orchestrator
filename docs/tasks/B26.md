# B26 — PR feedback shared by developers and reviewers

## Pickup and delivery

- Observed base: `origin/main` at `2ff7e5e`; maintainer-requested documentation task.
- Prerequisites: existing task execution protocol; remote PR inspection available.
- Branch: `task/B26-pr-review-feedback`; one task, one branch, one PR.
- Read [AGENTS](../../AGENTS.md), [execution protocol](../task-execution.md),
  [task contract](../task-contract.md) and [ADR-006](../adr/006-worker-service.md).
- Files: review protocol, agent/developer entry points, PR template, DoD,
  backlog/roadmap/handoff and append-only worklog/validation. No runtime changes.

## Objective and scope

Require actionable review findings on GitHub and developer intake/replies on the
same PR. Document the gap to sequential implementation/review with separate models.
Runtime orchestration, provider selection and merge are excluded; automation
needs its own future design and implementation cards.

## Implementation sequence

1. Inspect instructions, current code, remote PRs and milestone dependencies.
2. Define reviewer publication, developer replies and re-review at a fixed SHA.
3. Link the protocol from entry points and the publication checklist.
4. Record the automation gap without claiming runtime delegation is implemented.
5. Review both passes, check content/links, run suite/demo and publish.

## Validation and evidence to publish

Use content/link checks for all four documentation scenarios, `git diff --check`,
`node --test` and the fallback demo with captured exits. Report host gates as not
rerun because runtime is unchanged. Record both reviews, corrections, worklog,
validation, PR URL and verified base/head. No live model call or test PR comment
is required to validate documentation instructions.

## Final completion check

All rows have documentation evidence, checks pass, findings are corrected, and
one ready PR is pushed/verified under the execution protocol. A published protocol
is not evidence of an automated development/review cycle.
