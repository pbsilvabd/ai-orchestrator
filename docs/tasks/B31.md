## Objective and scope

B30 currently rejects every non-FIDO2 SSH signature, preventing a positive cryptographic
test without hardware. Add an explicitly configured, versioned software Ed25519 SSHSIG
profile. The profile must be named in both the signed canonical approval and trusted
service construction; omitted/unknown/mismatched profile selections refuse, with no
automatic downgrade. The FIDO2 profile remains separately selectable and still enforces
security-key algorithm, user-presence and user-verification flags.

The software profile proves only that the holder of the allowlisted software private key
signed the exact approval bytes. It does not prove hardware possession, user presence,
user verification, operator identity beyond the trusted signer mapping, or protection
against compromise of the signing account/host. The service consumes only public
`allowed_signers`/revocation data; signing key creation and approval authoring are outside
the service. The eventual composition must keep signing authority outside worker reach;
#46 must establish that boundary before any live activation. This task does not deploy
worker compartments, perform provider/live calls, sign with a maintainer key, or open
live composition.

Approval schema v1 is intentionally not silently migrated: schema v2 binds the profile
into canonical signed bytes and the verifier refuses v1 artifacts.

## Implementation sequence

1. Review all signature verifier, admission factory and approval producers/consumers.
2. Add schema v2 and two explicit profile identifiers; require trusted construction to
   choose one and require the signed approval to match it.
3. Restrict the software profile to ordinary Ed25519 SSHSIG and the FIDO2 profile to
   SSH security-key signatures with both UP and UV flags.
4. Test real `ssh-keygen -Y sign`/`-Y verify` positive software-profile admission using
   disposable keys, plus wrong signer/namespace, tampering, expiry, revocation, profile
   mismatch, single-use and no-side-effect refusal cases.
5. Update ADR, normative contract, this card, worklog, validation and continuation docs.
   Keep #46 deployment trust-boundary evidence explicitly open.
